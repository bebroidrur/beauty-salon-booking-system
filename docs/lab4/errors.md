# Єдина модель помилок

ApiError: обов’язкові `code` (стабільний машинний код) і `message` (текст для користувача); optional `details` — масив {field, message}. Невідомі поля заборонені. Дані клієнта, паролі, SQL, stack trace та внутрішні деталі не повертаються. Приклад: `{"code":"TIME_UNAVAILABLE","message":"Обраний час недоступний. Оберіть інший."}`.

| HTTP | Значення | Приклади code |
| --- | --- | --- |
| 400 | Некоректні параметри/запит | INVALID_REQUEST |
| 401 | Відсутній доступ або неправильні облікові дані | UNAUTHENTICATED, INVALID_CREDENTIALS |
| 403 | Недостатня роль або чужий запис | FORBIDDEN |
| 404 | Ресурс відсутній | NOT_FOUND |
| 409 | Конфлікт поточного стану | EMAIL_IN_USE, TIME_UNAVAILABLE, CURRENT_BOOKINGS_EXIST, CURRENT_BOOKINGS_CONFLICT, SCHEDULE_CONFLICT, BOOKING_CHANGE_CONFLICT, HISTORICAL_BOOKING |
| 422 | Невідповідність схеми або правил предметної області | VALIDATION_ERROR, BOOKING_RULE_VIOLATION, CANCELLATION_TOO_LATE |
| 500 | Неочікувана технічна помилка без розкриття деталей | INTERNAL_ERROR |

Усі оголошені 4xx/5xx операцій посилаються на ApiError, включно зі спеціалізованими прикладами. Нестача 2 годин, горизонт, несумісна/неактивна послуга при створенні — 422; зайнятість — 409. Пізнє скасування — 422 з пропозицією звернутися до адміністратора. Історичний запис — 409. Розмежування статусів — проєктна домовленість, SRS визначає поведінку, а не коди HTTP.

Prism із валідним запитом та `Prefer: code=409` лише відтворює приклад. Без Prefer перевіряється структура запиту й наявність Bearer; правильність пароля, роль, власність, строки та конфлікти не перевіряються. Стандартний режим Prism може вибрати оголошену 422/401 з ApiError; це фактично перевірено сценаріями. Власна діагностика Prism для невідомих маршрутів або режиму --errors не є продуктовим контрактом. Не слід використовувати --errors для наведеного набору перевірок.
