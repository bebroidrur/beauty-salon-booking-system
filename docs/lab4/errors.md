# Помилки фактичного HTTP API

Джерела: `salon/errors.py`, error handlers у `salon/app.py` та бізнес-перевірки
Service/Bookings. Відповідність маршрутам — [API-довідник](resource-model.md).

Сервер повертає `{"code":"…","message":"…"}`. Контракт допускає optional
`details: [{"field":"…","message":"…"}]`, але реалізація **не формує details**.
Неочікувані винятки перетворюються на 500 без stack trace або SQL у відповіді.

| HTTP | Фактичний code | Умова |
| --- | --- | --- |
| 400 | INVALID_REQUEST | Request body не JSON або JSON синтаксично пошкоджений. |
| 401 | UNAUTHENTICATED | Немає коректного Bearer, сесія невідома, або login не пройшов перевірку email/пароля. |
| 403 | FORBIDDEN | Недостатня роль; клієнт звертається до чужого запису. |
| 404 | NOT_FOUND | Відомий маршрут, але доменний ресурс не знайдено. |
| 404 / 405 | INVALID_REQUEST | Невідомий маршрут (зокрема slots) / непідтриманий HTTP-метод: HTTPException від Flask. |
| 409 | EMAIL_IN_USE | Повторна реєстрація email. |
| 409 | TIME_UNAVAILABLE | Конфлікт майстра або клієнта при створенні запису. |
| 409 | CURRENT_BOOKINGS_EXIST | Фізичне видалення послуги/майстра з актуальними записами. |
| 409 | CURRENT_BOOKINGS_CONFLICT | Вилучення з serviceIds майстра послуги актуального запису. |
| 409 | SCHEDULE_CONFLICT | Новий графік не вміщує актуальний запис майстра. |
| 409 | BOOKING_CHANGE_CONFLICT | Зміна історичного запису або невміщення/перетин при PATCH. |
| 409 | HISTORICAL_BOOKING | Скасування історичного, зокрема вже скасованого запису. |
| 422 | VALIDATION_ERROR | Схема, category, невідомий serviceIds, clientId не за роллю або семантично некоректний графік. |
| 422 | BOOKING_RULE_VIOLATION | Неактивність/несумісність при create, менше 2 год для клієнта, графік при create, горизонт >30 дат. |
| 422 | CANCELLATION_TOO_LATE | Клієнт скасовує менш ніж за 24 год; звернутися до адміністратора. |
| 500 | INTERNAL_ERROR | Неочікувана помилка або guard відкритого D-02–D-06. |

Приклад фактичного тексту з Bookings:

```json
{"code":"CANCELLATION_TOO_LATE","message":"До початку менше 24 годин. Зверніться до адміністратора."}
```

Валідація схеми зазвичай використовує 422; adapter вибирає 400, якщо для
операції в контракті немає 422. Порядок перевірок важливий: спочатку
автентифікація/роль, потім схема, потім доменні правила. Одна помилка може
закрити доступ до наступних перевірок; перелік не обіцяє їх одночасного показу.

Розходження з первісним проєктом ЛР4: login повертає UNAUTHENTICATED, а не
INVALID_CREDENTIALS; для невідомого URL використовується INVALID_REQUEST;
404 від createBooking не оголошено у відповідній операції OpenAPI.
Контракт не змінено. Guards і їхні точні умови наведені в API-довіднику.

Prism на порту 4010 відтворює контрактні приклади, не ці бізнес-перевірки.
`Prefer: code=409` у mock не є способом викликати конфлікт реального сервера.
Історичні докази mock перевірок залишаються в `logs/lab4/`.
