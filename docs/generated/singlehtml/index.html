Інформаційна система онлайн-запису до салону краси¶

Документація ЛР6 для фактичного навчального backend: Python, Flask, SQLite та email-outbox. Є REST API й CLI, графічного інтерфейсу немає. 17 контрактних операцій зареєстровано, listSlots відсутній; D-02–D-06 залишаються відкритими обмеженнями, не новими бізнес-правилами.

Python-довідник нижче створює Sphinx autodoc безпосередньо з модулів; Google-style docstrings обробляє Napoleon. HTTP-довідник та інструкція включені з наявних Markdown-джерел через MyST, без окремих копій тексту. Команди встановлення, запуску та генерації наведено в README репозиторію.

Інструкція користувача¶

Доступні REST API та адміністративний CLI; сторінок входу, календаря чи графічного кабінету немає. Приклади нижче — для локального сервера на порту 8000 і тестових даних. HTTP-довідник: операції, поля об’єктів, помилки.

Підготовка¶

  1. Установіть залежності й створіть адміністратора командами з README у корені репозиторію. Запустіть serve з БД runtime/salon.sqlite3.

  2. В іншому терміналі, теж з кореня репозиторію, задайте адресу:

BASE_URL='http://127.0.0.1:8000'

  1. Після кожного запиту перевіряйте HTTP-статус (curl -i показує його). Значення в кутових дужках далі замініть даними зі своїх відповідей; не надсилайте <service-id> або <token> буквально. Не використовуйте наведений демонстраційний пароль для реальних даних.

Клієнт: реєстрація й вхід¶

  1. Зареєструйте тестового клієнта:

curl -i -X POST "$BASE_URL/users" -H 'Content-Type: application/json' \
  -d '{"name":"Тестовий клієнт","phone":"+380000000000","email":"client@example.test","password":"demo-only-password"}'

Очікується 201 і User із id, профілем та role=client, без пароля. Збережіть id, якщо адміністратор записуватиме вас сам. Повторна реєстрація цього email дає 409 EMAIL_IN_USE — у такому разі перейдіть до входу.

  1. Увійдіть:

curl -i -X POST "$BASE_URL/sessions" -H 'Content-Type: application/json' \
  -d '{"email":"client@example.test","password":"demo-only-password"}'

Очікується 200 з accessToken, tokenType=Bearer і user. Невірний пароль — 401 UNAUTHENTICATED. Скопіюйте отриманий токен у змінну:

CLIENT_TOKEN='<accessToken клієнта>'

Токен дає доступ до ваших записів; не публікуйте його. Endpoint виходу, оновлення токена й відновлення пароля відсутній.

Адміністратор: підготувати каталог і графік¶

  1. Увійдіть через POST /sessions із email/паролем, які задали в create-admin (у запиті попереднього розділу замініть обидва значення). Збережіть окремий токен:

ADMIN_TOKEN='<accessToken адміністратора>'

  1. Створіть послугу:

curl -i -X POST "$BASE_URL/services" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Стрижка","description":"Стрижка волосся","price":500,"durationMinutes":60}'

Очікується 201 Service, active=true, currency=UAH. Запишіть її id:

SERVICE_ID='<id послуги>'

  1. Створіть майстра, який виконує цю послугу:

curl -i -X POST "$BASE_URL/masters" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"name\":\"Олена\",\"serviceIds\":[\"$SERVICE_ID\"]}"

Очікується 201 Master. Запишіть id:

MASTER_ID='<id майстра>'

  1. Новий майстер має неробочий графік. Для навчального прикладу встановіть щодня 09:00–18:00 (реальний графік салону задайте відповідно до потреб):

curl -i -X PATCH "$BASE_URL/masters/$MASTER_ID/schedule" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"weekly":{
    "monday":{"working":true,"interval":{"start":"09:00","end":"18:00"}},
    "tuesday":{"working":true,"interval":{"start":"09:00","end":"18:00"}},
    "wednesday":{"working":true,"interval":{"start":"09:00","end":"18:00"}},
    "thursday":{"working":true,"interval":{"start":"09:00","end":"18:00"}},
    "friday":{"working":true,"interval":{"start":"09:00","end":"18:00"}},
    "saturday":{"working":true,"interval":{"start":"09:00","end":"18:00"}},
    "sunday":{"working":true,"interval":{"start":"09:00","end":"18:00"}}
  },"exceptions":[]}'

Очікується 200 Schedule. Цей запит замінює весь тиждень та очищує винятки; не застосовуйте його до чинного графіка без наміру такої заміни. Невміщення актуальних записів у новий графік дає 409 SCHEDULE_CONFLICT. Перевірте збережені дані:

curl -i "$BASE_URL/masters/$MASTER_ID/schedule" -H "Authorization: Bearer $ADMIN_TOKEN"

Щоб задати відпустку, PATCH передає exceptions із об’єктами {"date":"YYYY-MM-DD","kind":"vacation","day":{"working":false}}; весь переданий масив замінює попередній. Повторні дати заборонені.

Клієнт: каталог і створення запису¶

  1. Каталог доступний без входу:

curl -i "$BASE_URL/services"
curl -i "$BASE_URL/masters"

Очікується 200 з items. Якщо масив порожній, каталог ще не налаштований. У списках видно і неактивні сутності; для нового запису обидві мають бути active=true, а serviceId має входити в serviceIds майстра.

  1. Погодьте час із салоном окремо: API доступних слотів ще немає. Для щойно створених тестових сутностей із графіком вище можна взяти 10:00 через два календарні дні. Команда обчислює дату й offset Kyiv, тому не залежить від застарілого прикладу дати:

STARTS_AT=$(.venv/bin/python -c 'from datetime import datetime,timedelta; from zoneinfo import ZoneInfo; print((datetime.now(ZoneInfo("Europe/Kyiv"))+timedelta(days=2)).replace(hour=10,minute=0,second=0,microsecond=0).isoformat())')

  1. Створіть власний запис, без clientId:

curl -i -X POST "$BASE_URL/bookings" \
  -H "Authorization: Bearer $CLIENT_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"serviceId\":\"$SERVICE_ID\",\"masterId\":\"$MASTER_ID\",\"startsAt\":\"$STARTS_AT\"}"

Очікується 201 Booking із status=confirmed, category=current, serviceSnapshot і розрахованим endsAt (для прикладу — 11:00). За конфлікту клієнта/майстра — 409 TIME_UNAVAILABLE: погодьте інший час. За межами графіка або менш ніж за 2 години — 422 BOOKING_RULE_VIOLATION.

BOOKING_ID='<id створеного запису>'

Адміністратор може створити запис аналогічним POST зі своїм токеном і додатковим clientId зареєстрованого клієнта. Йому не застосовується мінімум 2 години; решта перевірок залишається. Пошуку клієнтів за email через API немає.

Клієнт: перегляд і скасування¶

  1. Перегляньте власні актуальні записи та деталі:

curl -i "$BASE_URL/bookings?category=current" -H "Authorization: Bearer $CLIENT_TOKEN"
curl -i "$BASE_URL/bookings/$BOOKING_ID" -H "Authorization: Bearer $CLIENT_TOKEN"

Очікується 200; чужий запис дає 403 FORBIDDEN, невідомий ID — 404. Запис залишається актуальним до розрахованого завершення, включно з його початком.

  1. Скасуйте не пізніше ніж за 24 години до початку:

curl -i -X POST "$BASE_URL/bookings/$BOOKING_ID/cancellation" \
  -H "Authorization: Bearer $CLIENT_TOKEN"

Очікується 200 Booking, status=cancelled, category=history; час звільнено. За меншого строку — 422 CANCELLATION_TOO_LATE: зверніться до адміністратора поза системою. Повторне скасування — 409 HISTORICAL_BOOKING.

  1. Перегляньте історію:

curl -i "$BASE_URL/bookings?category=history" -H "Authorization: Bearer $CLIENT_TOKEN"

Очікується 200, запис є в items. Історія також містить записи, чий розрахований кінець минув; це не підтверджує фактичного виконання послуги.

Адміністратор: зміна запису й керування доступністю¶

Для цього розділу потрібен інший актуальний запис: можна повторити створення після скасування та оновити BOOKING_ID. Історичний запис змінити не можна.

  1. Погодьте новий час; у навчальному прикладі — 10:00 через три дні:

NEW_STARTS_AT=$(.venv/bin/python -c 'from datetime import datetime,timedelta; from zoneinfo import ZoneInfo; print((datetime.now(ZoneInfo("Europe/Kyiv"))+timedelta(days=3)).replace(hour=10,minute=0,second=0,microsecond=0).isoformat())')
curl -i -X PATCH "$BASE_URL/bookings/$BOOKING_ID" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"startsAt\":\"$NEW_STARTS_AT\"}"

Очікується 200 з новими startsAt/endsAt; snapshot послуги зберігається. При конфлікті — 409 BOOKING_CHANGE_CONFLICT, старий запис не змінюється. Клієнт із власним токеном не може виконати PATCH (403). Заміна послуги через serviceId оновлює snapshot; пара з майстром має бути сумісною.

  1. Адміністратор скасовує актуальний запис тим самим cancellation-запитом зі своїм токеном, зокрема коли залишилося менш ніж 24 години.

  2. Для заборони нових записів деактивуйте послугу (аналогічно майстра):

curl -i -X PATCH "$BASE_URL/services/$SERVICE_ID" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"active":false}'

Очікується 200, наявні записи збережені. Фізичний DELETE послуги/майстра можливий лише без пов’язаних записів: за актуальних — 409, за історичних поточна реалізація повертає guard D-06 (500). Деактивація не є видаленням.

Сповіщення й відомі обмеження¶

Email про створення/зміну/скасування ставиться в чергу, але успішний HTTP не засвідчує доставки. Оператор запускає SMTP worker за README. Для прикладу через два дні створюється reminder на 24 години до початку; при скасуванні він скасовується. Без worker/SMTP листа не буде; failed автоматично не повторюється.

  • GET /masters/{masterId}/slots повертає 404: вибору вільного часу немає.

  • На 29-й/30-й різниці дат, при деяких перенесеннях без попереднього reminder, несумісності чи неактивності при PATCH можливий 500 з D-02–D-06. Це незавершені правила, а не підтверджений запис; перевірте поточні дані через GET і зверніться до адміністратора. Точні умови — в API-довіднику.

  • Графік має один робочий інтервал на день; UI, SMS, оплати, reset password, самостійне перенесення клієнтом і кабінет майстра відсутні.

HTTP API: фактична реалізація¶

Оновлено в ЛР6 за salon/app.py, salon/service.py, salon/booking_service.py і salon/notifications.py. Зареєстровано 17 із 18 контрактних операцій. Це реалізований піднабір із відомими обмеженнями, не повна відповідність SRS. OpenAPI залишено без змін; вихідний проєкт ЛР4 і його приклади не означають, що кожен сценарій уже підтриманий.

Локальна адреса: http://127.0.0.1:8000 після запуску python -m salon serve. Prism на порту 4010 — окремий mock, а не сервер нижченаведених бізнес-правил. Графічного інтерфейсу немає. Є клієнт і адміністратор; майстер — сутність каталогу без облікового запису. Немає платежів, філій і кабінету майстра.

Спільні правила виклику¶

  • JSON-запити: Content-Type: application/json. Відповіді, крім 204, — JSON.

  • Захищені операції: Authorization: Bearer <accessToken> із POST /sessions. Токен непрозорий, не JWT. TTL, logout, refresh і відновлення пароля відсутні.

  • {serviceId}, {masterId}, {bookingId} — обов’язкові непорожні рядки в path, отримані з попередніх відповідей. Самі назви змінних не є ID.

  • Для операцій з requestBody тіла й вкладені об’єкти перевіряються схемою; зайві JSON-поля заборонені. Операції без requestBody, зокрема cancellation, фактично ігнорують передане тіло; воно не валідується й не змінює дію. PATCH має містити хоча б одне дозволене поле. Передані поля замінюються; для графіка замінюється вся передана weekly та/або весь exceptions.

  • Єдиний query-параметр реалізованих операцій — обов’язковий category=current або category=history у GET /bookings. Інші операції нижче не мають оголошених query-параметрів; невідомі query реалізація не відхиляє, але вони не дають пошуку, пагінації чи фільтрації.

  • Час — RFC3339 з явним offset; збережений показ — Europe/Kyiv.

  • Схеми запитів/відповідей і їхні поля наведені в схемах. У таблиці нижче — означає відсутність request body за контрактом.

  • Загальні помилки: 400 INVALID_REQUEST для не-JSON/пошкодженого JSON; 422 VALIDATION_ERROR для невідповідності схеми. Для захищених операцій 401 UNAUTHENTICATED, для недостатньої ролі — 403 FORBIDDEN. Неочікувані збої — 500 INTERNAL_ERROR. Повна семантика — помилки. Колонка помилок нижче доповнює ці спільні правила.

Заміна послуги адміністратором оновлює snapshot; сама зміна часу/майстра — ні.

category=history, якщо status=cancelled або endsAt ≤ поточний час; інакше current, включно з процесом надання послуги. Це не облік явки. Історичний запис незмінний. Скасування зберігає його, звільняє час, скасовує pending/failed нагадування. Суміжні інтервали не конфліктують; перетин перевіряється для майстра та клієнта в транзакції SQLite.

Email створюється в outbox у тій самій транзакції. API-відповідь не означає доставки листа: потрібен окремий налаштований worker. Нагадування створюється за 24 години до початку, якщо до початку залишилося ≥24 год. Після зміни надсилається changed, після скасування — cancelled. Доставка не має автоматичного retry; можливий дубль при збої після SMTP і до commit.

Запроєктовано, але не реалізовано¶

Контракт

Фактичний результат

GET /masters/{masterId}/slots?serviceId=…&date=YYYY-MM-DD

listSlots, public; path masterId, query serviceId/date обов’язкові; 200 Availability з масивом Slot

Маршрут не зареєстрований: 404 INVALID_REQUEST, без обчислення слотів. D-03 відкритий.

Slot та Availability у схемах описують лише проєкт. Не можна показувати клієнту календар доступних слотів на підставі цього API. Час доводиться погоджувати окремо; остаточна перевірка відбувається при записі.

Відомі межі реалізації¶

Ці guards повертають 500 INTERNAL_ERROR із повідомленням про D-рішення та rollback; це тимчасові обмеження ЛР5, не затверджені правила продукту:

Рішення

Реальна умова

D-02

При create/update різниця календарних дат у Kyiv дорівнює 29 або 30. Значення >30 дає 422. Внутрішні дати перевіряються іншими правилами.

D-03

При create/update початок ≤ now, якщо виконання дійшло до guard. Клієнтський create може раніше повернути 422 через правило 2 годин. Сітка 30 хв у коді не перевіряється; її прив’язка не погоджена.

D-04

Перенесення на ≥24 год від now, якщо для запису ніколи не було reminder у таблиці mail. Перенесення відкочується.

D-05

PATCH запису з послугою, якої немає в serviceIds майстра. При create це 422 BOOKING_RULE_VIOLATION.

D-06

PATCH запису з неактивною послугою/майстром; фізичне видалення сутності, яка має історичні записи (за актуальних спочатку 409).

Відоме розходження з OpenAPI: createBooking може повернути 404 NOT_FOUND для відсутньої послуги/майстра, хоча 404 для цієї операції не оголошено. Поточний довідник фіксує поведінку, не виправляє контракт чи сервер. Наявність ширшого списку responses у OpenAPI не доводить досяжність кожного коду в реалізації (наприклад, login не має гілки 409).

Схеми запитів і відповідей¶

Оновлено в ЛР6: ці схеми використовує runtime adapter для перевірки запитів і успішних відповідей. Slot/Availability — лише запроєктовані; details у ApiError фактично не формується.

Джерело контрактних структур: openapi.yaml, components/schemas. У таблиці required — обов’язкові поля; решта дозволених полів є optional. additionalProperties=false на об’єктах обмежує контракт його полями. Runtime застосовує перевірку тіла лише там, де операція має requestBody; для cancellation та інших операцій без тіла додатковий body ігнорується. Порожні PATCH заборонені minProperties=1. Числові обмеження й формат полів — проєктні рішення, див. адендум.

Списки повертають {items: […]}; порожній список є успішним 200. Пагінацію, сортування й обмеження розміру не вигадано. Slots потребує serviceId та date; bookings потребує category=current/history. Усі path ID — непрозорі непорожні рядки, не ключі БД.

Registration приймає name, phone, email, password; password writeOnly та відсутній у User/Session. Role не задається при реєстрації. Bearer — домовленість про транспорт доступу, не обіцянка JWT. Runtime використовує Werkzeug password hash і зберігає SHA-256 токенів; TTL/logout/refresh немає. Продуктовий TLS deployment не реалізовано.

204 не має тіла. Для кожної іншої відповіді задані application/json, схема та приклад. Статичні приклади використовують умовний now=2026-10-20T12:00:00+03:00; вони не стають часовим годинником mock і не адаптуються до дати запуску.

Обмеження полів, що перевіряються runtime¶

  • name у Registration/ServiceCreate/ServicePatch/MasterCreate/MasterPatch, phone, password та ID — непорожні рядки. Email має формат email. Телефон не має національного regex; додаткову парольну політику не введено.

  • description послуги — рядок; price — число ≥0, кратне 0.01; durationMinutes — ціле ≥1. Currency у відповіді — тільки UAH.

  • serviceIds — масив унікальних непорожніх рядків, може бути порожнім; Service перевіряє існування послуг. active — boolean.

  • startsAt/endsAt — date-time з offset; date — YYYY-MM-DD; робочі start/end — HH:MM від 00:00 до 23:59.

  • Day: {"working":false} або {"working":true,"interval":{"start":"09:00","end":"18:00"}}. Для Week потрібні всі сім днів. У ScheduleException kind — vacation, day_off чи changed_hours; перші два вимагають неробочого дня, останній — робочого.

  • status запису — confirmed/cancelled; category — current/history. ServiceList/MasterList/BookingList мають items відповідних об’єктів; поля кожного об’єкта наведено вище. Порожній результат — {"items":[]}.

Приклади запуску й послідовності запитів — інструкція користувача.

Помилки фактичного HTTP API¶

Джерела: salon/errors.py, error handlers у salon/app.py та бізнес-перевірки Service/Bookings. Відповідність маршрутам — API-довідник.

Сервер повертає {"code":"…","message":"…"}. Контракт допускає optional details: [{"field":"…","message":"…"}], але реалізація не формує details. Неочікувані винятки перетворюються на 500 без stack trace або SQL у відповіді.

Валідація схеми зазвичай використовує 422; adapter вибирає 400, якщо для операції в контракті немає 422. Порядок перевірок важливий: спочатку автентифікація/роль, потім схема, потім доменні правила. Одна помилка може закрити доступ до наступних перевірок; перелік не обіцяє їх одночасного показу.

Розходження з первісним проєктом ЛР4: login повертає UNAUTHENTICATED, а не INVALID_CREDENTIALS; для невідомого URL використовується INVALID_REQUEST; 404 від createBooking не оголошено у відповідній операції OpenAPI. Контракт не змінено. Guards і їхні точні умови наведені в API-довіднику.

Prism на порту 4010 відтворює контрактні приклади, не ці бізнес-перевірки. Prefer: code=409 у mock не є способом викликати конфлікт реального сервера. Історичні докази mock перевірок залишаються в logs/lab4/.

  • request_id – Correlation identifier for the request or mail job.

  • code – Optional safe error code; defaults to None.

Notes

Returns None. Callers supply safe values; this function does not redact arbitrary strings and must not receive secrets or personal data.

salon.mail_worker.run_once(store, clock, transport)¶

Deliver pending mail whose due time has arrived in one transaction.

Параметри:

  • store – Store providing a SQLite transaction.

  • clock – Callable returning an aware datetime for the due-time cutoff.

  • transport – Object with send(kind, payload) that delivers one message.

Повертає:

Number of messages successfully handed to the transport in this pass.

Notes

Transport exceptions mark jobs failed and are not propagated. Failed jobs are not automatically retried. The transaction remains locked during I/O; a crash after SMTP acceptance and before commit can duplicate delivery. Storage errors propagate to the caller.
