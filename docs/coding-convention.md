# Coding Convention — ЛР6

Конвенція стосується Python-коду цього репозиторію. Виконуваний backend —
`salon/`; `src/booking.py` — історичний приклад, не частина HTTP-застосунку.
Стек: Python 3.13, Flask 3.1.2, SQLite (`sqlite3`), PyYAML,
openapi-schema-validator; тести — pytest (pin 8.4.2; фактично у virtualenv 9.2.0). OpenAPI 3.0.3 описано в YAML.
Node-залежність Prism у `tests/lab4/package.json` — допоміжний mock ЛР4,
а не JavaScript frontend. Джерела версій: `requirements*.txt` і цей package.json.

## Правила

- Основа — [PEP 8](https://peps.python.org/pep-0008/) і
  [PEP 257](https://peps.python.org/pep-0257/).
- Чотири пробіли для відступів; один оператор на рядок; порожні рядки між
  визначеннями; пробіли навколо операторів і після ком. Файли UTF-8 із
  завершальним переводом рядка.
- Цільова ширина коду — 79 символів; проза docstrings бажано до 72.
  Довгі неподільні SQL-літерали, повідомлення та URL допускаються без зміни
  їхнього значення. Ruff formatter не гарантує жорсткого обмеження ширини.
- Імпорти групувати: стандартна бібліотека, сторонні пакети, локальний пакет;
  порядок автоматизовано правилом I. Не додавати імпорти із побічними діями
  лише заради документації.
- Модулі, функції, методи й локальні змінні — `snake_case`; класи — `CapWords`;
  константи — `UPPER_SNAKE_CASE`. Успадковані назви API не змінювати механічно.
- Назви `operationId`, JSON-поля (`clientId`, `serviceSnapshot`, `startsAt`),
  коди помилок, ролі й категорії точно зберігати з `spec/openapi.yaml`.
  Вони не підлягають перетворенню в `snake_case`.
- Публічні модулі, класи, конструктори, функції й методи документувати через
  `"""docstrings"""`: призначення, вхідні дані, результат, істотні винятки,
  побічні ефекти та передумови. Формат і приклади —
  [documentation-tags.md](documentation-tags.md).
- Коментарі пояснюють причину обмеження, наприклад D-04 чи crash window SMTP.
  Не видавати непогоджені рішення за прийняті вимоги.
- SQL-параметри передавати окремо від SQL-тексту. Зберігати межі транзакцій,
  перевірки доступу, snapshot, часовий пояс Europe/Kyiv та безпечний склад логів.
  Це правила супроводу поточної реалізації, не нова специфікація.
- Тести використовують наявні pytest markers `req`, `bdd`, `unit`,
  `integration`, `contract`. Пропуски повинні мати конкретну причину.

## Відтворення перевірок

Ruff 0.17.6 — інструмент розробки, конфігурація в `ruff.toml`.
[Офіційна документація конфігурації Ruff](https://docs.astral.sh/ruff/configuration/).
Перевіряються E4/E7/E9 (основні помилки оформлення), F (Pyflakes),
I (імпорти), D (docstrings, Google convention). Це вибраний набір автоматичних
перевірок, а не твердження, що всі положення PEP 8/257 можна довести лінтером.

```sh
.venv/bin/python -m pip install ruff==0.17.6
.venv/bin/python -m ruff check --no-cache salon src
.venv/bin/python -m ruff format --no-cache --check salon src
.venv/bin/python -m pytest tests/lab5 tests/network -q
.venv/bin/python scripts/check_lab4.py
```

Обсяг форматування ЛР6 — `salon/` і `src/`: усі 15 Python-файлів продукту
та історичної заготовки. Щоб не роздувати навчальні артефакти, тести й
допоміжні скрипти попередніх лабораторних проаналізовано, але не переписано.
Залишкові порушення зафіксовано у
[звіті](../logs/lab6-code-review.md). Для їхнього повторного огляду:

```sh
.venv/bin/python -m ruff check --no-cache --select E4,E7,E9,F .
```

Не застосовувати `--unsafe-fixes` і не змінювати контракт або бізнес-правила
заради lint. Локальні HTTP/SMTP тести потребують дозволу на loopback-сокети.
