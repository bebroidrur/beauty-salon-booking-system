## 2. Один цикл TDD і TEST-GATE

**RED:** виписати REQ → прямий AC/GWT (якщо є) → вхід/стан → очікуваний результат; створити найменший поведінковий тест. Запустити його на справному каркасі без реалізації правила. Зберегти команду, версії, HEAD і diff/хеш незакомічених змін, test ID, stdout/stderr, exit code та конкретний assertion. Помилка імпорту, відсутній пакет, непрацююча БД або нуль зібраних тестів — проблема середовища, не належний RED. Перед GREEN перевірити, що очікування походить зі специфікації, а не з написаного коду.

**TEST-GATE перед Feature (пропозиція, узгоджена з G-R2):** Human перевіряє REQ-ID, позитивні/негативні/граничні випадки, незалежність очікувань, справжній RED, повні Then і перелік BLOCKED. Рішення GO/REVISE/BLOCKED фіксується для конкретного пакета; зараз рішення відсутнє. Статистику coverage можна використовувати як допоміжну, непогоджений відсоток не вводити як критерій.

**GREEN:** реалізувати мінімум для тесту, дотримуючись OpenAPI request/response, статусів і ApiError. Перевіряти фактичну зміну/незмінність стану, а не лише HTTP-код. Для справжнього сервера не використовувати Prefer або статичний mock-token. Локальний GREEN не закриває інтеграційні побічні ефекти.

**REFACTOR:** лише після GREEN винести повторювані правила інтервалів, перевірки прав, формування snapshot та обробку помилок; відділити HTTP-адаптер, домен, сховище, годинник і email-порт настільки, наскільки потребує реалізація. Для конкурентності залишити гарантію в транзакційному шарі. Повторити той самий набір і регресію, зафіксувати diff та незмінність контракту. Не рефакторити заготовку наперед без поведінкового покриття.

**Підсумковий TEST-GATE:** усі погоджені тести пакета GREEN після рефакторингу, справжня REST/DB інтеграція для відповідних правил, немає прихованих skipped/xfail, відомі дефекти і BLOCKED перелічено. Неповний обсяг не називати повним прийманням системи.

## 4. Логування та одна нова вимога addendum

**Кандидат `REQ-F-065` — аудит дій і системних подій. Статус: PROPOSED, не baseline.** Номер наступний після REQ-F-064; перед майбутнім погодженням повторно перевірити, що він вільний. У baseline немає функції аудиту: REQ-NF-006 обмежує вміст діагностики, а процесне `/logs` зберігає докази перевірок.

Пропонований текст: система повинна створювати структуровану подію аудиту для кожної спроби входу, створення/зміни/скасування запису, зміни послуги/майстра/графіка, а також для запуску/результату email-задачі й технічної помилки. Подія містить час UTC, кореляційний ID, тип дії, непрямий ідентифікатор актора (або system/anonymous), тип та непрямий ID ресурсу за наявності, результат і безпечний код причини. Події не містять паролів, токенів, повних імені/телефону/email, тіл запитів, деталей записів або текстів листів. HTTP-відповіді й endpoints не розширюються.

Запропоновані AC (ще не затверджені):

- `AC-REQ-F-065-01`: для успішної та відхиленої зміни/входу журнал містить подію з усіма застосовними полями й правильним результатом; відмова не фіксується як успіх.
- `AC-REQ-F-065-02`: системна email-задача та її результат корелюють із початковою операцією; технічна помилка має код причини й не розкриває контрольні секрети/ПД.

Запропонований BDD: Given чинний власний запис із початком за 12h; When клієнт намагається скасувати його; Then відмова за REQ-F-035 зберігає стан, а подія аудиту містить action=cancel, outcome=rejected, код причини та кореляцію без деталей запису. Це приклад нової вимоги, не доданий GWT baseline.

Планові `L5-ADD-001` (P: успішна дія й system event), `L5-ADD-002` (N: відхилення/технічна помилка/секрети), `L5-ADD-003` (B: дві одночасні операції мають різні кореляції, пов'язані події — однакову) посилаються на **запропоновану REQ-F-065** і BLOCKED до SPEC-ADDENDUM-GATE.

План реалізації після погодження: спочатку RED на capture sink; потім middleware кореляції, logger з дозволеним переліком полів, доменні події після фактичного результату транзакції, системні події email; далі GREEN і рефакторинг спільного формату. Технічні журнали runtime зберігати окремо від доказів Gates; у Git лише санітизовані контрольні приклади. Політики строку зберігання, доступу до журналів, ротації та поведінки при відмові sink ще не погоджені — визначити перед прийманням, не додавати вигадані числові межі.

**SPEC-ADDENDUM-GATE (план):** підготувати diff вимоги/AC/BDD/матриці, обґрунтування новизни, аналіз приватності (REQ-NF-004/006), витрат, впливу на D-40–D-44 і ризики R-07/R-10/R-16; показати відсутність змін OpenAPI або окремо подати необхідні зміни на review. Людина ухвалює рішення до реалізації нової поведінки. Baseline зберігається, нова версія/addendum має власний хеш і зв'язок з попередньою. Зараз рішення **NOT REVIEWED**. Це вимога майбутнього процесу, не запит на підтвердження поточного аудиту.

## 5. Фінальна верифікація та валідація

**Верифікація («чи правильно реалізовано специфікацію»):** перевірити повні unit/integration/REST suites, реальну конкурентність, ownership, часові межі, snapshot та rollback, email-задачі, OpenAPI-схеми; звірити REQ–AC–GWT–test–code–log, baseline hash і дозволені addendum diff. Після рефакторингу повторити регресію, `git diff --check`, перевірити докази на секрети. NF оцінювати лише за погодженими умовами. G-R3/G-R6 і D-40/D-41 дають пакет доказів, а не автоматичне людське приймання.

**Валідація («чи розв'язує система задачу користувача»):** людина в ролі клієнта проходить каталог → вхід → запис → власні деталі → скасування/історію; у ролі адміністратора — керування каталогом/графіком, створення клієнту, перенесення й конфліктні відмови. Спостерігати повідомлення й листи, перевірити зрозумілість причин відмов. За відсутності UI можна провести лише часткову API-валідацію; не приймати браузерні REQ-NF-007/008. Зафіксувати фактичну особу/роль, дату, збірку, сценарій, очікуване/спостережене, дефекти, рішення accepted/revise і обмеження. Зараз людей, дат приймання та результатів немає.

Завершення ЛР5: справжні RED/GREEN/REFACTOR докази погодженого обсягу, review TEST-GATE, окреме рішення addendum, фінальні verification/validation, актуальна матриця та перелік залишкових ризиків. Не переносити історичні PASS ЛР4 на ці етапи.

## 6. Команди запуску

Виконувати з кореня репозиторію. Наявна перевірка плану (пройшла в цьому аудиті):

```sh
python3 scripts/check_lab3_scenarios.py
```

Відновлення інструментів контракту за наявним lock-файлом (залежності потребують доступу до PyPI; встановлення тут не виконувалось):

```sh
python3 -m venv /tmp/beauty-lab5-contract-venv
/tmp/beauty-lab5-contract-venv/bin/python -m pip install -r tests/lab4/requirements-lock.txt
/tmp/beauty-lab5-contract-venv/bin/python scripts/check_lab4.py
```

Опційне відтворення mock, не бізнес-тести (npm install і локальний порт потребують відповідних дозволів середовища):

```sh
mkdir -p /tmp/beauty-lab5-prism
cp tests/lab4/package.json tests/lab4/package-lock.json /tmp/beauty-lab5-prism/
npm ci --prefix /tmp/beauty-lab5-prism --cache /tmp/beauty-lab5-npm-cache
/tmp/beauty-lab5-prism/node_modules/.bin/prism mock spec/openapi.yaml --host 127.0.0.1 --port 4010
```

В іншому терміналі:

```sh
/tmp/beauty-lab5-contract-venv/bin/python scripts/check_lab4.py --mock http://127.0.0.1:4010
```

**Майбутні команди pytest — лише проєкт інтерфейсу запуску.** До створення залежностей і тестів вони не працездатні; зараз немає команди запуску реального backend. На етапі каркаса зафіксувати pytest і потрібні драйвери в окремому lock-файлі; тоді запровадити:

```sh
python -m pytest tests/unit -q
python -m pytest tests/integration -q
python -m pytest tests/api -q
python -m pytest tests/unit tests/integration tests/api -q --junitxml=logs/lab5/test-gate/green/junit.xml
```

Для RED запускати конкретний node ID; для REFACTOR — той самий набір із новим шляхом журналу. Не перезаписувати попередні докази; застосовувати унікальний run ID. Зберігати exit code самого runner, а не `tee`. Код pytest 5 (немає тестів), import errors та відсутня БД не є успішним GREEN чи доказом потрібного RED.
