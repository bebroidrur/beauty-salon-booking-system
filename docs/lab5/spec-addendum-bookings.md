# SPEC-ADDENDUM — вузький аудит подій Bookings

Статус: **PROPOSED / NOT APPROVED**. Цей документ не змінює baseline SRS, OpenAPI або матрицю baseline.

## Запропонована вимога

`REQ-F-065-B` — для кожної операції Bookings, яка змінює стан (`POST /bookings`, `PATCH /bookings/{bookingId}`, `POST /bookings/{bookingId}/cancellation`), система повинна створювати структуровану внутрішню подію аудиту після успішного commit або після відхилення операції. Подія містить UTC-час, кореляційний ID запиту, тип операції, непрямий ID актора, ID ресурсу, результат (`accepted` або `rejected`) і безпечний код причини. Подія не містить пароль, токен, email, телефон, ім'я клієнта, тіло запиту або деталі запису.

Це звуження первинної пропозиції `REQ-F-065` до модуля Bookings. Воно не додає HTTP endpoint, не змінює відповідь API та не вводить політику зберігання, ротації або доступу до журналів. Такі політики потребують окремого рішення.

## Узгодженість із Bookings

Вимога узгоджується з REQ-F-009, REQ-F-027–029, REQ-F-034–044 і REQ-F-056–064: журнал фіксує результат уже визначених операцій і не змінює їхню семантику. Вона підтримує REQ-NF-006 як запропонований контроль діагностики та не суперечить REQ-NF-004. Розширена пропозиція на login, каталог, графік і технічні події вилучена з цього addendum.

Запропоновані критерії: `AC-REQ-F-065-B-01` — успішне створення, перенесення та скасування мають `accepted` з кореляцією; `AC-REQ-F-065-B-02` — конфлікт, пізнє скасування або чужий доступ мають `rejected`, без зміни запису та без секретів/ПД. Запропонований сценарій: Given власник має запис менш ніж за 24 години; When він скасовує; Then API повертає `CANCELLATION_TOO_LATE`, стан не змінюється, а подія має `cancel`, `rejected`, кореляцію та безпечний код.

Критерії й сценарій мають статус пропозиції; вони не додаються до `spec/acceptance-criteria.md` або `spec/given-when-then.md` до погодження.
