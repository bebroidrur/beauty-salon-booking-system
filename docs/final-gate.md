## Суттєві невідповідності

1. Початковий задум і SRS описують адаптивний вебзастосунок, а фактичний результат ЛР5 має REST API та CLI без графічного інтерфейсу.
2. `listSlots` присутній у затвердженому OpenAPI, але не реалізований; два тести пропущені через D-03.
3. Частина часових, reminder і catalog правил має PARTIAL через відкриті D-02–D-06.
4. Нефункціональні UI, browser, TLS, recovery, availability та benchmark-вимоги не підтверджені поточним обсягом.

Ці розбіжності не виправляються зміною SRS, OpenAPI або бізнес-логіки в межах цього етапу. Потрібне рішення людини: прийняти навчальний API/CLI-обсяг як подання лабораторної, погодити addendum/обмеження або повернути цикл на доопрацювання.

## Перевірка саме погодженого обсягу

Суттєвої невідповідності, яка блокувала б приймання погодженого модуля Bookings, після ручної валідації не виявлено. Реалізовані operationId, ролі, конфлікти, snapshot, історія, скасування, перенесення, графік і outbox відповідають зафіксованим тестовим доказам та прийняті Human у межах ЛР5. `listSlots`, UI та повна SRS свідомо не входять до цього GO. D-02–D-06 і зовнішня email-доставка залишаються явно задокументованими обмеженнями, а не прихованими невідповідностями.

## Рішення

**GO для погодженого скороченого обсягу.** Реалізований модуль і його залежності пройшли технічну верифікацію та ручну перевірку в межах погодженого викладачем обмеження ЛР5 до одного API-модуля.

**REVISE для повної початкової SRS.** `listSlots`, UI та частина NF/відкритих D-рішень потребують наступного SDD-циклу. Це рішення не змінює SRS і не оголошує весь продукт прийнятим.

## Історія рішення

Попередня редакція від 2026-11-26 містила `REVISE` до завершення Human validation. Після підтвердження користувачем 2026-11-28 це рішення уточнено: `GO` лише для погодженого скороченого обсягу, а `REVISE` збережено для повної SRS.
